# 教師資料生成與複核規格

目前 quality-v3 由本次 GPT/Codex 助理撰寫對話種子與回覆規則，再結合既有程式錯誤標籤及 Docker 紀錄產生資料。沒有呼叫另一個 GPT API，沒有獨立教師審查，也沒有使用私人學生對話。

若之後以 GPT API 擴充，僅傳送訓練 split 的專案自編題意、程式及執行證據；不要傳送驗證或最終測試的題目與標準答案。API 金鑰只用本地環境變數保存。每筆資料必須記錄實際模型 ID、生成時間、題目與輸入雜湊，並保留未採用的回覆與拒收理由。

可使用的教師指令：

> 你是繁體中文 C++17 程式教師。請先核對題意、目前程式、實際執行證據及最新學生問題。給一個直接回應問題、正確且連貫的 assistant 回覆，不要輸出思考過程。預設只給符合指定提示層級的局部引導；學生明確要求完整解答時才給完整 C++17。不能捏造已執行或通過測試，不能因為學生已通過測資仍硬找錯。學生回答上一輪問題後，先承接，再推進一步。所有可執行片段只用 C++17，標記 cpp，解釋用繁體中文。若證據不足，具體說明缺少的資訊。輸出 reply、使用的證據編號、是否包含可執行程式，以及待人工複核的疑點。

複核與資料篩選：

1. 逐字核對引述的測資與編譯資訊，禁止將未執行當作已通過。
2. 生成的完整 C++ 必須交給 Docker 判題；不能在 Windows 主機直接執行。
3. 對局部修正建立正確版與錯誤版的最小差異，修正後需重跑原失敗測資。
4. 以不同的提問與回覆策略處理新手、卡關、已回答、錯誤想法、已通過與完整解答；不要大量複製同一句提示。
5. 由另一位教師或獨立評閱者檢查題意忠實度與推理；同一個生成模型的自評不能當作獨立證據。
6. 評估原始輸出及整合網站後的輸出須分開記錄，避免把繁體轉換、格式化或參考解答查表的效果算成模型微調的效果。

參考：[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)、[Evaluation best practices](https://developers.openai.com/api/docs/guides/evaluation-best-practices)。結構化格式能約束欄位，不能保證內容正確。
